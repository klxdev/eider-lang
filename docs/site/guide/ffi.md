# Calling C, and calling Eider from C

Eider compiles to C, so it can call C functions directly and be called from C and C++.
Both directions are deliberately narrow: only integers, `bool` and strings cross, no
pointers reach Eider code, and every call into C is marked so that unmanaged code is
always visible, in the source and in the package graph.

## Calling C: `extern "c"`

Declare the C function with its signature, without a body:

```eider
extern "c" fn abs(n: i32) -> i32
extern "c" fn strlen(s: str) -> usize
extern "c" fn atoi(s: str) -> i32

fn main() uses io, ffi {
    let a = unsafe { abs(-42) }
    let n = unsafe { strlen("eider") }
    let v = unsafe { atoi("1234") }
    print(a)
    print(n)
    print(v + 1)
}
```

```output
42
5
1235
```

Three things make a call to C:

1. **The declaration** names the C symbol. Parameters and the result must be C-safe: an
   integer type (`i32` is `int32_t`, `u64` is `uint64_t`, `usize` is `size_t`, ...),
   `bool`, or `str` (a `const char *` to NUL-terminated text); the result may also be `()`.
   Anything else (a `String`, a List, a record, an `inout` parameter) is E0803.
2. **`uses ffi`** on the function that makes the call (E0201 without it).
3. **An `unsafe` block** (or an `unsafe fn`) around the call (E0802 without it):

```eider,compile_fail=E0802
extern "c" fn abs(n: i32) -> i32

fn main() uses io, ffi {
    print(abs(-1))
}
```

`unsafe` is the programmer's promise that the C function is memory-safe for these
arguments; the compiler can't check C. Keep unsafe code small by wrapping it in a function
with an ordinary, safe signature:

```eider
extern "c" fn toupper(c: i32) -> i32

/// ASCII upper case, through the C library.
fn upper(c: u8) -> u8 uses ffi {
    unsafe { toupper(c as i32) as u8 }
}

fn shout(s: String) -> String uses ffi {
    let mut out = String.from("")
    for c in s.bytes() { out.push_byte(upper(c)) }
    out
}

fn main() uses io, ffi {
    print(shout(String.from("quiet please")))
}
```

```output
QUIET PLEASE
```

An `unsafe fn` is a function whose body may call C and whose callers must themselves use
`unsafe`; prefer a safe wrapper like `upper` above.

### `ffi` and packages

Inside a package, `ffi` propagates like any capability: `shout` needs it because `upper`
does. **Across a package boundary it doesn't**: callers in other packages declare only the
real capabilities a wrapper reaches (`fs`, `io`, ...). Instead, a package with `extern`
functions, `unsafe fn`s or `unsafe` blocks must be granted `ffi` by every package that
depends on it, in `eider.toml` ([Capabilities](capabilities.md#ffi-unmanaged-code-stays-in-its-package)):

```toml
[deps.zlib_binding]
path = "../zlib_binding"
uses = ["ffi"]
```

That is how the toolchain itself is built: `core/sys.ei` and `core/os.ei` are the only Eider
files in the repository with `extern` declarations, and they bind only the small C core
(`core/eider_core.c`, one OS call per function). Everything above, std included, is
checked Eider.

### Linking a C library

C functions outside the C library need their library linked: `-l <name>` (repeatable)
passes `-l<name>` to the C compiler for `build`, `run`, `test` and `build --lib`. Extra
flags (include or library directories) go in `EIDER_CFLAGS`:

```sh
EIDER_CFLAGS="-L/opt/foo/lib" scripts/ei run app.ei -l foo
```

### Limits

- No pointers, buffers, structs or callbacks cross into C from Eider. A C API that needs
  them is wrapped in a small C function first, or bound by passing data a byte at a time
  as `core/sys.ei` does.
- No floating-point types yet.
- An extern can't be used as a function value (it would escape `unsafe`).
- Extern functions are global names, not namespaced by module.
- Extern declarations use an ELF assembler label for the symbol; Mach-O (macOS) would need
  a prefix and isn't supported yet.

## Calling Eider from C and C++: `export fn`

Mark the functions a C program may call with `export`, and build a library:

```eider,ignore
// temps.ei
type Reading = { celsius: i32, sensor: u32 }

export fn to_fahrenheit(c: i32) -> i32 { c * 9 / 5 + 32 }

export fn warmer(a: Reading, b: Reading) -> u32 {
    if a.celsius >= b.celsius { a.sensor } else { b.sensor }
}

export fn is_freezing(c: i32) -> bool { c <= 0 }

export fn unit() -> str { "Fahrenheit" }
```

```sh
scripts/ei build --lib temps.ei -o temps
```

```text
built libtemps.a, libtemps.so, temps.h
```

(The block is marked `ignore` because a library has no `main` to run; the docs' tests run
programs.) The header declares each export as `eider_<name>`, with records of C-safe fields
as structs:

```c
/* generated by eider: C interface */
#ifndef EIDER_TEMPS_H
#define EIDER_TEMPS_H
#include <stdint.h>
#include <stdbool.h>
#ifdef __cplusplus
extern "C" {
#endif
typedef struct R_Reading R_Reading;
struct R_Reading { int32_t f_celsius; uint32_t f_sensor; };
int32_t eider_to_fahrenheit(int32_t c);
uint32_t eider_warmer(R_Reading a, R_Reading b);
bool eider_is_freezing(int32_t c);
const char* eider_unit(void);
#ifdef __cplusplus
}
#endif
#endif
```

A C program links either library; both carry the Eider runtime and the C core, so nothing
else is needed:

```c
#include <stdio.h>
#include "temps.h"

int main(void) {
    printf("%d %s\n", eider_to_fahrenheit(100), eider_unit());
    R_Reading a = { 21, 1 }, b = { 25, 2 };
    printf("warmer: sensor %u\n", eider_warmer(a, b));
    printf("freezing: %d\n", eider_is_freezing(-3));
    return 0;
}
```

```sh
cc -std=c11 -o app app.c libtemps.a              # static
cc -std=c11 -o app app.c -L. -ltemps             # shared (LD_LIBRARY_PATH=. ./app)
```

```text
212 Fahrenheit
warmer: sensor 2
freezing: 1
```

The header is valid C++ too (`extern "C"`), so C++ code includes it the same way.

Rules and behaviour:

- Exported functions take and return C-safe types, and records made only of C-safe
  fields (E0803 otherwise); they can't be generic (E0805). A library needs no `main` but
  at least one `export fn` (E0805). `scripts/ei check --lib file.ei` checks one without
  building, `scripts/ei emit-header file.ei` prints the header.
- A trap inside the library (an overflow, a failed bound) ends the whole process with exit
  code 101, as in an Eider program.
- Strings returned as `str` are string literals; they live as long as the program.
- Each header's include guard comes from the library's name (`EIDER_TEMPS_H` for
  `temps.h`), so one C file can include the headers of several Eider libraries, as long
  as they don't export records of the same name.

For JavaScript and the browser, the same `export fn`s become a WebAssembly module:
[WebAssembly](wasm.md).
