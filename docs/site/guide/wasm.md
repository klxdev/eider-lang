# WebAssembly

`scripts/ei build --wasm` turns a file's `export fn`s into a WebAssembly module, with
TypeScript declarations and a small JavaScript loader, for Node or the browser. The module
is self-contained: Eider's runtime and a tiny freestanding C library are compiled in, and
it imports only two host functions (writing text, and the time).

## Requirements

- clang with the `wasm32` target, and `wasm-ld` (set `WASM_CC` to choose the clang).
- Node or a browser to run the result.

Only these commands need the wasm32 target and `wasm-ld`; building native programs needs
clang 17 or newer, and building the compiler itself only a C compiler.
`scripts/verify.sh` skips its WebAssembly leg, with the reason, when they are missing.

## A module

```eider,ignore
// calc.ei: functions for JavaScript
export fn add(a: i32, b: i32) -> i32 { a + b }

export fn fib(n: u32) -> u64 {
    let mut a: u64 = 0
    let mut b: u64 = 1
    for i in 0..n {
        let t = a + b
        a = b
        b = t
    }
    a
}

export fn is_even(n: i32) -> bool { n % 2 == 0 }

export fn sum_to(n: i32) -> i64 {
    let mut l: List[i64] = List.new()
    for i in 0..n { l.push(i as i64) }
    l.sum()
}

export fn log_twice(n: i32) uses io {
    print(n)
    print(n * 2)
}

export fn div(a: i32, b: i32) -> i32 { a / b }
```

(The block is marked `ignore` because a module has no `main`; the docs' tests run
programs. It was built and run as shown below.)

```sh
scripts/ei build --wasm calc.ei -o calc
```

```text
built calc.wasm, calc.d.ts, calc.js
```

Inside, the module is ordinary Eider: Lists, Strings, Maps, records, closures, generics,
`print` and every check (overflow, bounds) work as in a native build. Only the exported
signatures are restricted.

## The TypeScript declarations

```text
// generated by eider
export interface EiderExports {
  add(a: number, b: number): number;
  fib(n: number): bigint;
  is_even(n: number): boolean;
  sum_to(n: number): bigint;
  log_twice(n: number): void;
  div(a: number, b: number): number;
}
export interface EiderImports { [name: string]: (...args: any[]) => any }
export function load(wasm: BufferSource | WebAssembly.Module, imports?: EiderImports): Promise<EiderExports>;
```

32-bit integers become `number`, 64-bit ones `bigint`, `bool` `boolean`, `()` `void`, a
`String` a `string` and a `List[u8]` a `Uint8Array`. The loader's result also has the
module's `memory`.

## Using it from JavaScript

```text
// main.mjs
import { readFileSync } from "fs";
import { load } from "./calc.js";

const calc = await load(readFileSync("calc.wasm"));
console.log(calc.add(2, 3), calc.fib(50), calc.is_even(4), calc.sum_to(100));
calc.log_twice(21);
try {
  calc.div(1, 0);
} catch (e) {
  console.log("trapped:", e.constructor.name);
}
```

```text
$ node main.mjs
5 12586269025n true 4950n
21
42
eider: runtime error: division by zero (lib:28)
trapped: RuntimeError
```

- `print` output goes through the `eider_write` import: to `process.stdout` in Node, to
  `console.log` elsewhere. Pass your own in `load`'s second argument to redirect it; it is
  called with the module's memory as a third argument, so it can read the text:
  `{ eider_write(ptr, len, memory) { text += new TextDecoder().decode(new Uint8Array(memory.buffer, ptr, len)); } }`.
- A trap prints its message and becomes a WebAssembly `unreachable`, which JavaScript
  sees as a `RuntimeError`. The module stays usable afterwards only as far as the trap left
  its memory consistent; treat a trap as fatal, as in a native program.
- In a browser, pass `fetch("calc.wasm")`'s bytes (or a compiled `WebAssembly.Module`) to
  `load`.

## Rules

Checked by `scripts/ei check --wasm file.ei`:

- Exported functions take integers, `bool`, `String` and `List[u8]`, and return one of
  those or `()` (E0806). Other Lists, records, `Option` and `Result` can't cross the
  boundary yet.
- No threads: a module that uses `spawn`, `Task`, `Mutex` or `Chan` is E0806.
- No `main` (the module is a library) and at least one `export fn` (E0805).

```text
error[E0806]: parameter `name` has type str; WebAssembly exports take only integers, bool, String and List[u8]
  --> bad.ei:1:17
  |
1 | export fn greet(name: str) -> i32 { 1 }
  |                 ^
```

## Known limits

- Records, other Lists, `Option` and `Result` across the boundary are planned (the design is
  `docs/design/typescript_models.md`).
- Unsigned results above the signed range come back as negative numbers (or negative
  BigInts) in JavaScript.

## Strings and bytes

```eider,ignore
export fn greet(name: String) -> String {
    let mut s = String.from("hello, ")
    s.append(name)
    s
}

export fn checksum(data: List[u8]) -> u64 {
    let mut t: u64 = 0
    for b in data { t += b as u64 }
    t
}
```

```text
const m = await load(bytes);
m.greet("world")                     // "hello, world"
m.checksum(new Uint8Array([1, 2]))   // 3n
```

The loader copies an argument into the module's memory (UTF-8 for a string; one containing
a NUL character is a `TypeError`, as is a value of the wrong type), calls the function, and
frees the copy; a result is copied out and freed the same way. Nothing stays allocated
between calls. The module's `memory` is part of what `load` returns.
